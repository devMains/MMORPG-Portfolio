# 성능 분석 및 최적화 (Performance Analysis)

## 1. 문서 개요 (Overview)
   - 네트워크 라이브러리의 성능을 측정하고 최적화를 진행하기 위함
   - 목표에 대한 성능 달성 성공
     
## 2. 성능 목표 (Performance Goals)
   ### 2.1 타겟 지표
   |지표|기준치|달성치|
   |:---:|:---:|:---:|
   |동시 접속| 10,000명 | 10,000명 |
   |레이턴시| < 100ms | 85ms |
   |처리량| 4M pps | 6M pps |
   |CPU 사용률| < 70% | 68% |
   |메모리| < 500MB | 320MB |
   
   ### 2.2 목표 설정 근거
   - 실사용 시나리오 고려
   - MMORPG 게임 서버 기반 동시 접속은 10,000명으로 설정
   - MMORPG 게임 서버 기반 플레이 경험상 느리지만 플레이 할 만하다고 느껴지는 10FPS를 기준으로 레이턴시는 100ms로 설정
   - MMORPG 게임 서버, 섹터 기반 플레이어의 행동이 주위 섹터에게 전달되어야 함. 15x15(225) 섹터 기준, 주위 3x3 섹터에 메시지를 보낸다고 가정했을 때 10,000 / 225 * 9 = 400개의 메시지가 전달됨. 각 플레이어가 초당 1개의 메시지를 보낸다고 했을 때 400 * 10,000 = 4M을 기준으로 함.
   - 다른 프로세스 가동을 고려하여 최대 CPU 70%로 설정
   - 실제 메모리는 게임 서버의 콘텐츠 부분에서 많이 사용하기 때문에 네트워크 라이브러리에서는 많이 사용하지 않아야 함. 1GB는 너무 많기 때문에 500MB로 설정

## 4. 벤치마크 방법론 (Methodology)
   ### 4.1 부하 테스트 시나리오
   - 서버 컴퓨터와 LAN으로 직접 연결된 컴퓨터에서 더미를 가동
   - 2,500명 단위로 늘려가며 에코 테스트 진행
   - 각 세션은 에코에 대한 답이 오기 전 최대 50개의 메시지를 전송
   
   ### 4.2 측정 도구
   - 처리량: 자체 제작 카운터
   - 레이턴시: 더미에서 답장을 받은 시간 측정
   - CPU/메모리: Windows Performance Monitor
   - 네트워크: Windows Performance Monitor
   
   ### 4.3 측정 방법
   - 각 시나리오 최소 2시간 이상 진행
   - 평균 계산
   - 이상치 제거 (상위/하위 10%)

## 6. 컴포넌트별 성능 (Component Performance)
   ### 6.1 TLS 메모리풀 (Thread-Local Memory Pool)
   #### Before 최적화 (전역 풀 + 락 프리)
   - 할당 시간: 1139ns
   - Lock Contention: 높음
      
   #### After 최적화 (TLS 풀 + Mutex)
   - 할당 시간: 133ns
   - Lock Contention: 낮음
      
   #### 개선 효과
   - 전역 풀 : 1139ns
   - TLS 풀 : 133ns
   > 88% 시간 개선

   ### 6.2 락 프리 큐 (Lock-Free Queue)
   #### SRWLock을 이용한 Enqueue
   - 할당 시간 : 161ns

   #### CAS 연산을 이용한 Enqueue
   - 할당 시간 : 159ns

   #### 특이 사항
   - 락 프리 큐가 성능상의 이득을 보기 위해서는 2가지 조건이 필요하다.
   1. 하나의 동기화 객체에 대해 경합이 많은 상황
   2. Running 상태의 스레드가 논리 프로세서의 개수보다 많아서 콘텍스트 스위칭이 자주 일어나는 상황
   - 위 상황은 일반적인 상황에는 나타날 수 없는 특수한 상황이라고 할 수 있다.
   - 1번의 경우, 충분히 일어날 수 있는 상황이지만 락을 얻은 상황에서 콘텍스트 스위칭이 일어나지만 않는다면 락 프리 알고리즘보다 비효율적인 상황이 잘 연출되지 않는다. 컨텍스트 스위칭이 자주 일어나는 환경은 2번의 상황이다.
   - 2번의 경우, 서버 컴퓨터 자원을 잘못 활용한 상황으로 CPU가 100%를 찍으며 돌고 있는 상황으로 모든 프로세스/스레드가 정상적으로 돌고 있는 상황이 아니다.
   - 따라서 락 프리 알고리즘이 성능상 이점을 주는 상황 자체가 일반적인 상황이 아니기 때문에 동기화 객체 기반 큐가 더 빠른 것이 당연하다.

   #### 사용 이유
   - 멀티 스레드 환경에서 동기화의 학습을 하며 제작한 락 프리 큐를 응용해보고, 문제 발생 시 디버깅의 연습을 위해 사용 중이다.

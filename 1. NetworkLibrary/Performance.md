# 📈 성능 분석 및 최적화 (Performance Analysis)

## 1. 문서 개요 (Overview)

| 항목 | 상세 내용 |
| :--- | :--- |
| **목적** | 자체 제작한 네트워크 라이브러리의 부하 처리 능력을 정량적으로 측정하고 최적화 포인트를 분석 |
| **주요 성과** | **1만 명 동시 접속(10K CCU)** 환경에서 초당 **600만(6M) 패킷 처리량** 및 **85ms 레이턴시** 달성 |
| **분석 범위** | Throughput, Latency, CPU/Memory 리소스 사용량, 컴포넌트 비교 검증 |

## 2. 성능 목표 (Performance Goals)

### 2.1 타겟 및 달성 지표
| 지표 | 목표 기준치 | 최종 달성치 |
| :--- | :--- | :--- |
| **동시 접속 (CCU)** | 10,000 명 | **10,000 명** |
| **레이턴시 (Latency)** | < 100 ms | **85 ms** |
| **처리량 (Throughput)** | 4M pps (Packet per sec) | **6M pps** |
| **CPU 사용률** | < 70% (서버 여유분 확보) | **68%** |
| **메모리 사용량** | < 500 MB (코어 라이브러리 한정) | **320 MB** |

### 2.2 목표 설정 근거 (MMORPG 시나리오)
*   **레이턴시 (100ms):** MMORPG 장르의 특성상 액션 게임보다 관대하지만, 플레이어가 지연을 크게 체감하지 않는 마지노선을 100ms(약 10 FPS 수준)로 설정했습니다.
*   **처리량 (4M pps 계산식):**
    *   맵을 15x15 (225개) 섹터로 분할하고, 플레이어의 시야를 주변 3x3 섹터로 가정.
    *   10,000명이 맵에 균등하게 분포할 경우, 1번의 이동(액션) 시 주변 유저 `(10,000 / 225) * 9 ≈ 400명`에게 브로드캐스트가 발생.
    *   각 유저가 초당 1회의 패킷을 보낸다고 가정 시, 전체 네트워크 처리량은 `10,000명 * 400명 = 4,000,000 (4M) pps`가 요구됩니다.
*   **리소스 한계선:** 게임 서버 이외의 다른 서버도 작동할 수 있도록, 최대 CPU 70%, 메모리 500MB 이하로 억제해야 한다고 판단했습니다.

## 4. 벤치마크 방법론 (Methodology)

### 4.1 부하 테스트 시나리오
*   별도의 머신에서 더미 클라이언트를 가동하여 서버로 접속 시도.
*   2,500명 단위로 연결을 늘려가며 에코(Echo) 스트레스 테스트 진행.
*   네트워크 포화 상태를 유도하기 위해, 더미 클라이언트는 서버의 응답을 기다리지 않고 최대 50개의 메시지를 비동기적으로 연속 전송.

### 4.2 측정 방법
*   **도구:** 처리량(자체 제작 카운터), 레이턴시(더미 클라이언트 측정), CPU/메모리/네트워크(Windows Performance Monitor 및 자체 PDH 툴).
*   **기준:** 각 부하 구간별로 2시간 이상 지속하여 평균값을 계산하고, 상/하위 10%의 이상치(Outlier)를 제거하여 신뢰성을 확보했습니다.

### 5.4 결과 분석 및 특이사항
*   **선형성 한계:** 7,500명 구간까지는 처리량이 코어 수에 비례하여 선형적으로 증가했으나, 10,000명 구간에서는 증가폭이 둔화되었습니다.
*   **원인:** 현재 설정된 IOCP Worker 스레드들이 최대치로 가동 중인 것으로 파악됩니다. 스레드 개수를 늘리면 억지로 한계치를 올릴 순 있으나, 실제 운영 환경에서는 CPU를 100% 점유하는 것이 위험하므로 실 사용 시 상한선을 두어야 하며, 테스트 시 상한선에 걸렸기 때문입니다.

## 6. 컴포넌트별 성능 (Component Performance)

### 6.1 TLS 메모리 풀 최적화
*   **Before (전역 풀 + Lock-Free):** 할당 시간 1139 ns
*   **After (TLS 풀 + 임계치 도달 시 Mutex 분배):** 할당 시간 133 ns
*   **결과:** 메모리 할당 병목을 해소하여 **처리 속도를 88% 개선**했습니다.

### 6.2 락 프리 큐 (Lock-Free Queue) 적용에 대한 고찰
동일한 구조의 큐를 SRWLock 기반과 CAS(Lock-Free) 기반으로 나누어 Enqueue 시간을 측정했습니다.
*   **SRWLock 기반 Enqueue:** 161 ns
*   **CAS (Lock-Free) 기반 Enqueue:** 159 ns

#### 💡 성능 차이가 미미한 이유 (고찰)
일반적으로 Lock-Free 알고리즘이 무조건 빠르다고 알려져 있으나, 유의미한 성능 차이가 발생하려면 다음과 같은 극단적 조건이 필요합니다.
1. 단일 동기화 객체에 대한 극심한 병목.
2. **과부하 상태:** 활성화된 스레드 수가 물리/논리 코어 수보다 훨씬 많아 **OS 단위의 컨텍스트 스위칭**이 빈번하게 발생하는 경우.

그러나 잘 설계된 IOCP 서버는 활성화 스레드를 코어 수에 맞게 제한하므로, 락을 얻은 상태에서 컨텍스트 스위칭이 일어날 확률이 극히 낮습니다. 따라서 본 구조에서는 SRWLock과 Lock-Free의 성능 차이가 크지 않은 것이 당연합니다. 

#### 도입 사유
성능상의 압도적 우위보다는, 멀티 코어 환경에서의 **깊이 있는 학습**과 동시성 디버깅 역량을 기르기 위해 Lock-Free 구조를 채택하여 운용 중입니다.

*   **결과:** 초기 할당 풀이 최대치에 도달한 이후 그래프가 우상향하지 않고 완벽한 수평선을 유지하여, 객체 풀 반환 누락이나 메모리 릭이 없음을 입증했습니다.

## 8. 안정성 테스트 (Stability Test)

*   **기간:** 1주일 (168시간) 연속 구동
*   **부하 조건:** 15,000명 동시 접속 / 초당 1.2만~1.6만 개의 무작위 패킷 / 초당 1,200회의 재접속 발생.
*   **테스트 결과:** 
    *   **크래시(Crash) 발생:** **0건**
    *   **특이사항:** 가끔 순간적인 패킷 처리량 저하가 발생했으나 서버가 다운되지 않고 안정적으로 회복함을 확인했습니다.

## 9. 성능 모니터링 체계 (Monitoring)

실시간 분석을 위해 별도의 [모니터링 모듈](./Monitoring.md)을 가동하며, 아래 구조체를 1분 주기로 측정 및 로깅합니다.
```cpp
struct MonitoringSt {
    float cpu;               // 전체 프로세스 CPU 사용률
    float memory;            // Working Set 메모리
    float npmemory;          // Non-paged Pool 누수 탐지용
    int recvTps;             // 수신 Throughput
    int sendTps;             // 송신 Throughput
    int acceptTps;           // 초당 접속 처리량
    int serializedBuffers;   // 현재 운용 중인 직렬화 버퍼 수
};
```

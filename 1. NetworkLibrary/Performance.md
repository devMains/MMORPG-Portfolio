## 4. 벤치마크 방법론 (Methodology)
   ### 4.1 부하 테스트 시나리오
      **시나리오 1: 램프업 테스트**
      ```
      0초: 0명 접속
      10초: 1,000명 접속 (초당 100명 증가)
      20초: 5,000명 접속 (초당 400명 증가)
      30초: 10,000명 접속 (초당 500명 증가)
      → 60초간 유지
      ```
      
      **시나리오 2: 스파이크 테스트**
      ```
      10초 평온 → 5초 내 10,000명 급증 → 30초 유지
      ```
      
      **시나리오 3: 지속 부하 테스트**
      ```
      10,000명 동시 접속 상태로 24시간 유지
      ```
   
   ### 4.2 측정 도구
      - **처리량**: 자체 제작 카운터
      - **레이턴시**: Windows QueryPerformanceCounter
      - **CPU/메모리**: Windows Performance Monitor
      - **네트워크**: Wireshark, netstat
   
   ### 4.3 측정 방법
      - 각 시나리오 10회 반복
      - 평균/중앙값/P95/P99 계산
      - 이상치 제거 (상위/하위 10%)

   ### 6.3 락프리큐 (Lock-Free Queue)
      #### Before 최적화 (Mutex 기반)
      ```
      스레드: 10개 Producer
      처리량: 50K enqueue/sec
      평균 대기: 15μs
      Lock Contention: 높음
      ```
      
      #### After 최적화 (Lock-Free)
      ```
      스레드: 10개 Producer
      처리량: 230K enqueue/sec
      평균 대기: 3μs
      Lock Contention: 없음
      ```
      
      #### 개선 효과
      | 지표 | Mutex | Lock-Free | 개선율 |
      |------|-------|-----------|--------|
      | 처리량 | 50K/s | 230K/s | **360% 향상** |
      | 평균 지연 | 15μs | 3μs | **80% 감소** |
      | P99 지연 | 120μs | 18μs | **85% 감소** |
      | CPU 사용 | 85% | 45% | **47% 감소** |
      
      #### 스레드별 확장성
      | 스레드 수 | Mutex (K/s) | Lock-Free (K/s) | 배율 |
      |----------|-------------|-----------------|------|
      | 1 | 48 | 52 | 1.08x |
      | 2 | 50 | 98 | 1.96x |
      | 4 | 52 | 180 | 3.46x |
      | 8 | 51 | 210 | 4.12x |
      | 10 | 50 | 230 | 4.60x |
   
   ### 6.4 TLS 메모리풀 (Thread-Local Memory Pool)
      #### Before 최적화 (전역 풀 + Mutex)
      ```
      할당 시간: 300ns
      ```

      #### After 최적화 (TLS 풀)

## 19. 교훈 및 인사이트 (Lessons Learned)
   ### 19.1 성공 요인
      ```
      1. 측정 우선: "측정할 수 없으면 개선할 수 없다"
      2. 병목 집중: 상위 20% 핫스팟이 80% 영향
      3. 단계적 최적화: 한 번에 하나씩 개선
      4. 실제 부하: 합성 벤치마크 < 실제 시나리오
      ```
   
   ### 19.2 실패 경험
      ```
      ❌ 과도한 최적화: 가독성 저하로 버그 증가
      ❌ 잘못된 가정: 추측 대신 측정해야 함
      ❌ 미세 최적화: 1% 개선에 너무 많은 시간
      ```
   
   ### 19.3 최적화 원칙
      ```
      1. Make it work (동작하게)
      2. Make it right (올바르게)
      3. Make it fast (빠르게)
      ↑ 이 순서를 지킬 것!
      ```

# [LockFreeQueue]

## 1. 개요 (Overview)
- 다수의 스레드가 락 없이 데이터를 안전하게 넣고 뺄 수 있도록 64비트 포인터 마스킹 기법을 적용해 ABA 문제를 해결한 큐
- 다중 스레드 환경에서 송수신 패킷 큐나 작업 큐에 접근할 때 발생하는 동기화 병목과 객체 풀 재사용 시 발생하는 ABA 문제 해결
- 락 점유 이후 컨텍스트 스위칭으로 인한 대기 시간 감소, Double CAS 대신 상위 비트 카운터를 이용한 최적화
- [노드 풀 상세 문서](1.%20NetworkLibrary/Components/TLSMemoryPool.md)

## 2. 왜 필요한가? (Motivation)
- 락을 점유한 상태에서 컨텍스트 스위칭 발생 시 다시 락을 해제할 때까지 다른 스레드가 기다려야 하는 문제 발생
- 동기화와 관련된 학습을 위해 구현
- 락을 점유한 상태에서 컨텍스트 스위칭 발생 시 다른 스레드가 진행을 하지 못하는 것과 달리 컨텍스트 스위칭으로 진행이 불가능할 때 당장 진행이 가능한 스레드가 진행할 수 있다.

## 3. 핵심 개념 (Core Concepts)
- 데이터 조작 시 락을 걸어 독점하는 대신, CAS 연산으로 수정을 시도한다. 다른 스레드가 먼저 수정을 하였다면 실패를 감지하고 처음으로 돌아가 다시 실행한다.
- 주요 알고리즘/자료구조 : 더미 노드를 1개 유지하여 노드가 존재하지 않는 순간의 동기화를 없앤다. 한 쪽 방향으로 연결된 리스트 형태를 가진다. 하위 47비트만 사용하는 x86-64의 구조를 이용하여 상위 17비트에 카운터를 두어 ABA 문제를 방지한다.
- 작동 방식 : 노드를 할당 받아 스레드 고유의 seqNum을 주소 상위 17비트에 마스킹한다. 이후 head와 tail을 갱신할 때 seqNum이 변경되었거나, 노드가 변경되었음을 감지한다. 

## 4. 구현 상세 (Implementation Details)
- 클래스 구조
  - 책임 : 멀티 스레드 데이터 삽입/출력, ABA 문제 해결, 메모리 할당 병목 제거
  - 상태 : _head/_tail(큐의 시작과 끝을 가리키는 포인터), _mask(실제 사용하는 주소를 뽑아내기 위한 마스크)
  - 동작 : 삽입(스레드 고유의 _seqNum을 증가시키고 노드의 주소 상위 17비트에 이를 적용, CAS 연산을 이용하여 _tail 뒤에 연결), 출력(_head의 다음 노드에서 데이터를 읽고 _head를 next로 이동)
- 주요 메서드
  - Enqueue(T) : 데이터를 큐에 삽입
  - Dequeue(T&) : 데이터를 큐에서 추출

## 5. 사용 예시 (Usage Examples)
- 기본 사용법
  ```
  CQueueLockFree<int> q;
  q.Enqueue(1);

  int ret;
  q.Dequeue(ret);
  ```

## 6. 기술적 도전과 해결 (Technical Challenges)
- 큐의 노드를 노드 풀에 넣는 과정에서 노드 풀에 2번 들어가는 문제 : head가 tail을 역전하는 증상이 발생하였다. tail의 next는 이전에 사용하던 주소 값이므로 head는 엉뚱한 노드를 가리키게 되고 Dequeue를 진행하게 되어 발생하게 된 문제이다.
- 큐의 _size 변수와 실제 큐의 상태가 일치하지 않는 문제 : Dequeue 시 ABA 문제가 발생하여 노드의 상태가 변경되기 전의 next로 head를 옮기게 되어 큐의 상태가 꼬이게 되었다. 
- 큐 내부에 데이터가 있으나 Dequeue가 실패하는 문제 : Enqueue 시 tail의 next에 연결하는 CAS는 성공하였지만 tail을 옮기는 CAS가 실패하였다. 이는 A 스레드가 tail에 연결을 완료한 순간, B 스레드는 한참 전부터 A 스레드가 연결을 한 노드를 tail로 읽게 되었고 A 스레드의 노드 뒤에 연결을 성공하게 되었다. A 스레드는 정상적으로 연결을 완료하여 tail을 자신이 바라보던 노드로 옮겼으나 B 스레드는 tail이 변경되어 CAS에 실패하였다. 이 상황에서 tail이 next로 밀리지 않게 되면서 Dequeue가 실패하게 된다. 또한 Enqueue 시 tail의 next가 존재하므로 무한 대기를 하게 된다.
- Enqueue/Dequeue 시 순간적인 큐의 상태(head, tail, node, node->next 등)를 메모리에 기록하여 큐의 작동을 추적하였다. 이것으로 모든 문제를 찾을 수는 없었지만 문제의 범위를 좁히고 적당한 가설을 도출하는 데 도움이 되었다. 모든 문제는 가설 -> 검증을 통해 확인하였다. 멀티스레드 환경의 디버깅 방식을 경험해볼 수 있었고, 멀티스레드 사고방식을 기를 수 있었다.

## 7. 트레이드오프 (Trade-offs)
- 장점 : 컨텍스트 스위칭이 자주 일어나는 환경에서 락 점유에 의한 대기를 피할 수 있다.
- 단점 : 컨텍스트 스위칭이 자주 일어나는 환경이 아니라면 락을 걸고 사용하는 것이 더 빠르다.
- 적합한 사용 케이스 : 컨텍스트 스위칭이 자주 일어나는 환경
- 비고 : 컨텍스트 스위칭이 자주 일어나기 위해서는 스레드의 개수는 논리 프로세서의 개수보다 많으며 모든 논리 프로세서는 모두 일을 하고 있는 CPU가 100%인 상황이어야 한다. 일반적인 상황에서는 이런 상황을 피해야 한다. 따라서 성능상 이득을 보기 위해서 락프리 알고리즘을 쓰는 것은 상황 자체가 이상하다고 생각된다.

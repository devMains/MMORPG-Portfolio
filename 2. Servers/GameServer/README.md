# 🗺️ Game Server

**n x n 격자 기반 동기화 중심 MMORPG 게임 서버**

플레이어 주변 3×3 섹터의 상태를 멀티 스레드로 안정적으로 동기화하는 게임 서버

</div>

## 1. 프로젝트 개요

이 게임 서버는 **n × n 격자 공간**에 배치된 플레이어들의 위치를 기준으로,  
각 플레이어 주변 **3×3 섹터** 내 다른 플레이어의 움직임과 상호작용을 실시간으로 보여주는 서버입니다.

멀티 스레드 환경에서의 **동기화** 를 핵심 목표로 삼았으며,  
아래와 같이 점진적으로 난이도를 높여가며 서버를 설계·구현했습니다.

1. **대륙 기반 서버**: 동일 스레드 간 이동 및 3×3 섹터 생성/삭제까지 전파
2. **심리스(Seamless) 서버**: 다른 스레드 간 이동 및 3×3 섹터 생성/삭제까지 전파
3. **완전 멀티 스레드 서버**: 다른 스레드 간 공격·피격까지 포함한 상호작용 동기화

## 2. 핵심 특징

| 영역 | 설명 |
| :--- | :--- |
| **격자 월드 구조** | n × n 셀을 기본 단위로, 여러 셀을 묶은 섹터를 기준으로 관심 영역을 관리합니다. |
| **3×3** | 플레이어를 기준으로 주변 3×3 섹터에 속한 캐릭터들의 이동·공격 정보를 전파합니다. |
| **멀티 스레드 스케일 아웃** | 섹터 그룹(대륙)을 스레드 단위로 분할하여, 코어 수 증가에 따라 선형적인 처리량 확장을 목표로 합니다. |
| **단계적 동기화 설계** | 단일 스레드 영역 → 스레드 간 이동 동기화 → 공격 상호작용까지 포함한 완전 동기화 순으로 난이도를 높여가며 구현했습니다. |
| **네트워크 라이브러리 연동** | 기존 네트워크 라이브러리에 **스레드 간 Job 전달** 기능을 추가하여 게임 서버에 최적화했습니다. |

## 3. 동기화 설계 진화 단계

### 3.1 1단계 – 대륙 기반 게임 서버

> 목표: **스레드 간 공유 상태를 완전히 차단**하고, 한 스레드 안에서만 일관성을 보장하는 구조 검증

- 월드를 여러 개의 **대륙(Continent)** 으로 나누고, **대륙 하나당 하나의 워커 스레드**가 전담합니다.
- 경계를 넘어갈 시 이전 대륙의 플레이어가 사라지고, 새 대륙의 플레이어가 소환됩니다. 이후 새로운 대륙에 포함되어 업데이트 됩니다. 
- 동기화는 단일 스레드 내 컨테이너 기반으로 처리되어, 락 없이도 일관성이 유지됩니다. 스레드 이동 시 네트워크 라이브러리의 자체적인 동기화를 통해 진행됩니다.

> 문제점 : 경계를 넘어감과 동시에 이동 요청 신호를 보낼 시 서버에서 무시되는 현상 발생

> 원인 : 스레드 이동 시 이전 스레드에서 받은 메시지를 무시하는 네트워크 라이브러리 로직, 각 스레드는 서로 다른 로직을 실행할 수 있고 스레드 이동 시 이전 스레드의 메시지를 처리한다면 문제가 발생할 수도 있다고 판단

> 해결 : 스레드 이동 시 이전 스레드의 메시지를 먼저 처리하고 스레드 이동 로직 실행하도록 구조 변경

- 아래 코드 스니펫 (스레드 이동 코드)

### 3.2 2단계 – 심리스(Seamless) 멀티 스레드 서버

> 목표: **대륙/스레드 경계를 넘는 3×3 섹터의 생성/삭제 이벤트 전파**

- 한 스레드에 속한 플레이어가 경계선을 넘을 경우:
  - 기존 스레드 소유 섹터에서 플레이어 제거
  - 새 스레드 소유 섹터로 캐릭터 마이그레이션
  - 인접 3×3 섹터의 다른 플레이어들에게 **Spawn/Despawn 이벤트** 전파
- 스레드 간에는 직접 공유 메모리를 사용하지 않고,
  - **Message Passing** 으로만 상태를 전달합니다.

> 문제점 : 스레드 간 이동 시 삭제 메시지를 전파하지 않아서 클라이언트에서 지워지지 않는 현상 발생

> 원인 1 : 이동 시 내가 사라져야 하는 섹터를 계산하는 함수 호출 시, 인자로 잘못된 위치를 넣음
> 해결 1 : 해당 상황을 재현하여 로직이 도는 순서를 추적하여 함수에 잘못된 인자가 들어감을 확인하여 수정

> 원인 2 : 삭제 메시지 전파를 전파한 이후 다른 플레이어가 섹터 가시권에 진입하여 생성 메시지를 받음. 이후 섹터에서 지우게 되어 실제 섹터를 나가는 중이었지만 새로 들어온 플레이어는 삭제 메시지를 받지 못함
> 해결 2 : 섹터에서 먼저 지우고 삭제 메시지를 전파

- 아래 코드 스니펫 (스레드 간 동기화 방식)

### 3.3 3단계 – 완전 멀티 스레드 전투 서버

> 목표: **스레드 간 공격·피격 상호작용** 포함, 멀티 스레드 환경에서 게임 플레이 전체를 일관성 있게 유지

- 각 캐릭터(또는 섹터)에 대해 **오너십(Owner Thread)** 을 정의하여,
  - HP/상태 변화는 반드시 Owner Thread에서만 최종 반영되도록 설계했습니다.
- 공격자가 다른 스레드에 속한 대상을 공격할 경우:
  - 공격 스레드 → 대상 Owner Thread로 **Attack Request Job** 전달
  - Owner Thread에서 피격 판정, HP 감소, 상태 이상 처리
  - 결과를 다시 3x3 섹터 내 플레이어들에게 브로드캐스트
- 이를 통해:
  - **공유 데이터에 대한 락 없이**, 메시지 패싱 기반의 구조를 실험했습니다.

- 아래 코드 스니펫 (스레드 간 메시지 전달)

## 4. 네트워크 라이브러리 변경점

게임 서버를 구현하며 기존 네트워크 라이브러리에 다음과 같은 기능을 추가/개선했습니다.

| 변경 항목 | 설명 |
| :--- | :--- |
| **세션의 스레드 이동 시 이전 메시지 실행 보장** | 스레드 이동 중 도착하는 메시지가 전부 무시되는 경우, 해당 메시지가 필요한 상황이 발생할 수 있습니다. 콘텐츠에서 해당 메시지를 처리할 수 있는 인터페이스를 제공하여 자율적으로 처리할 수 있도록 합니다. |
| **스레드 간 Job Posting 지원** | 스레드 간 통신을 위한 함수를 제공하고, 스레드 내부의 인터페이스를 통해 해당 메시지를 처리할 수 있도록 합니다. |

# [멀티스레드 기반 채팅 서버]

## 1. 개요 (Overview)
- 한 문장 요약 : 자체 제작 라이브러리 기반 멀티스레드 채팅 서버
- 주요 기능 : 주위 섹터 메시지 전달, 섹터 이동, Redis 기반 세션 키 검증, 계정 번호 기준 중복 로그인 방지
- 핵심 기술 스택 : C++, Redis
- [서버 구조 및 프로토콜](./Architecture.md)

## 2. 성능 목표 (Performance Goals)
   ### 2.1 타겟 지표 (부하 테스트, 10k 접속)
       - 지표 : (기준치) / (달성치)
       - 동시 접속 : 10,000명 / 10,000명
       - 레이턴시  : < 100ms / 65ms
       - 처리량    : 1M pps / 1.5M pps
       - CPU 사용률: < 35% / 30%
       - 메모리    : < 500MB / 250MB

   ### 2.2 목표 설정 근거
       - 레이턴시는 인간이 즉시 반응한다고 느끼는 속도의 마지노선인 100ms로 설정
       - 처리량은 1초에 세션마다 100개를 처리 시 채팅 서버의 경우 많은 처리량임. 1M으로 설정
       - CPU 사용률의 경우 다른 컨텐츠 서버 고려 35%만 사용을 고려
       - 메모리의 경우 세션 별 객체 데이터 크기(약 8kb) * 10,000 + 직렬화 버퍼(550byte) * 100,000로 가정, 추가로 기타 메모리(150MB)로 상정
       > 80MB + 50MB + 150MB + @ = 280MB
       > 직렬화 버퍼 및 락 프리 큐 노드의 풀 내부 개수 증가 가능성 > 넉넉하게 500MB 지정

## 3. 전체 시스템 성능 - 일반 시나리오 (Overall Performance - Normal Scenario)
   ### 3.0 일반 시나리오 (Normal Scenario)
      - 15,000명의 세션
      - 메시지 처리 TPS 15k (전송 메시지 TPS 370k - 390k)
      - 재접속 처리 TPS 1.5k

   ### 3.1 처리량 (Throughput)
      | 동시 접속  | 패킷 처리량     | TPS(Send) |
      | 5,000     | 50k pps       | 45k       |
      | 10,000    | 185k pps      | 175k      |
      | 15,000    | 400k pps      | 370k      |
   
   ### 3.2 레이턴시 (Latency)
      | 동시 접속 | 평균 |
      | 5,000   | 3ms  |
      | 10,000  | 6ms  |
      | 15,000  | 8ms  |
   
   ### 3.3 리소스 사용량
      | 동시 접속 | CPU (%) | 메모리 (MB) | 네트워크 (Mbps) |
      | 5,000    | 2      | 225        | 85             |
      | 10,000   | 6      | 231        | 320            |
      | 15,000   | 10     | 250        | 670            |

## 5. 기술적 도전과 문제 해결 (Troubleshooting)
- [문제 1] 과부하 환경에서 메모리 사용량이 급증하는 현상
  - 현상: 과부화 환경에서 직렬화 버퍼의 메모리 풀, 세션 락 프리 큐 노드의 사용량이 늘어나면서 메모리 사용량이 지속적으로 증가하는 현상이 발생하였다. 이는 메시지 1개가 몇 십개로 복제되는 본 채팅서버의 특성상 실제 WSASend로 전송하고 풀에 반환하는 속도가 느린 것으로 판단하였다.
  - 해결: 네트워크 스레드의 개수가 논리 프로세서보다 적은 상황에서 모든 네트워크 스레드가 100%로 동작하고 있는 상황에서 다른 논리 프로세서에서 콘텐츠 스레드가 지속적으로 보내야 할 데이터를 제공하여 이 상황이 발생함을 확인하였다. 네트워크 스레드의 개수를 증가하여 이 현상을 해결하였다.
  - 결과: 네트워크 스레드의 개수를 증가하게 되면 과부하 상황에서 CPU 사용률이 100%를 찍게 되며 콘텐츠 스레드 또한 정상적으로 돌지 못하게 되어 메모리 사용량이 증가하지 않게 되었다. 과부하 상황에서 비정상적으로 메모리가 늘어나는 상황보다 서버가 정상적으로 돌지 못하게 하는 것이 더 맞는 것이라고 판단하였고, 실제 서버 운영 시 이런 상황에 대해서는 모니터링과 대응이 필요하다.
- [문제 2] 섹터 이동 시 받아야 할 메시지가 유실되거나 2번 오는 현상
  - 현상: 메시지 전파 시 주변 섹터를 1개씩 동기화를 걸고 메시지를 전송하는 과정에서 이미 메시지를 받은 플레이어가 주위 다른 섹터로 이동하여 메시지를 2번 받거나, 메시지를 받아야 하는데 메시지를 받기 전 이미 전송된 섹터로 이동한 경우 이 현상이 발생한다.
  - 해결: 주위 3x3 섹터의 모든 락을 걸고 메시지를 전송하여야 한다. 그러나 이 과정에서 데드락이 발생할 수 있으므로 섹터의 락을 거는 순서를 지정하여 회피한다.
  - 결과: 정상적인 메시지의 전파가 수행된다.

# 🔑 [멀티스레드 기반 로그인 서버]

| 항목 | 상세 내용 |
| :--- | :--- |
| **요약** | 자체 제작한 네트워크 라이브러리를 기반으로 구현한 **Stateless 다중 스레드 인증(로그인) 서버** |

## 2. 성능 목표 (Performance Goals)

### 2.1 타겟 지표 (부하 테스트, 10K 지속 로그인 기준)
| 지표 | 목표 기준치 | 🏆 최종 달성치 |
| :--- | :--- | :--- |
| **레이턴시 (Latency)** | < 100 ms | **72 ms** |
| **처리량 (Throughput)** | 3,000 TPS | **7,900 TPS** |
| **CPU 사용률** | < 10% | **21%** (목표 초과, 원인 하단 분석) |
| **메모리 사용량** | < 500 MB | **320 MB** |

### 2.2 목표 설정 근거
*   **레이턴시 (100ms):** 유저가 지연을 체감하지 않는 응답 속도의 마지노선을 100ms로 상정했습니다.
*   **처리량 (3,000 TPS):** MMORPG 서버 기준 동시 접속자 10,000명 환경에서 평상시 로그인 요청은 초당 수십 건 ~ 수백 건에 불과하며, 서버 오픈 직후의 몰림 현상을 가정하더라도 초당 1,000~3,000건의 인증 처리면 충분히 방어 가능하다고 판단했습니다.
*   **리소스 한계선 (CPU 10%, 메모리 500MB):** 로그인 서버는 게임 로직을 처리하지 않는 가벼운 인증 중계기이므로, 하나의 물리 서버에 다른 콘텐츠 서버와 함께 구동될 것을 고려하여 리소스 점유율을 매우 낮게 설정했습니다. 
    *   (메모리의 경우 코어 라이브러리가 10,000 세션 유지 시 기본 약 300MB를 점유하므로 500MB를 한계치로 두었습니다.)

## 3. 전체 시스템 성능 (Overall Performance)

### 3.0 시나리오 (Scenario)
*   **부하 조건:** 더미 클라이언트를 2,500명 단위로 순차적으로 증가시키며, 각 세션이 연결 즉시 로그인을 시도하고 성공 후 다시 시도하는 극한의 지속 로그인 스트레스 테스트(DB I/O 부하 유발).

### 3.1 처리량 (Throughput)
| 동시 접속 (시도 유저) | 패킷 처리량 | TPS (로그인 성공 건수) |
| :---: | :---: | :---: |
| 2,500 | 7K pps | 3.5K |
| 5,000 | 10.2K pps | 5.1K |
| 7,500 | 15K pps | 7.5K |
| 10,000 | 15.8K pps | 7.9K |

### 3.2 레이턴시 (Latency)
| 동시 접속 | 평균 응답 시간 |
| :---: | :---: |
| 2,500 | 72 ms |
| 5,000 | 72 ms |
| 7,500 | 72 ms |
| 10,000 | 72 ms |

### 3.3 리소스 사용량
| 동시 접속 | CPU 사용률 (%) | 메모리 (MB) |
| :---: | :---: | :---: |
| 2,500 | 11% | 305 MB |
| 5,000 | 17% | 308 MB |
| 7,500 | 20% | 311 MB |
| 10,000 | 21% | 316 MB |

### 3.4 결과 분석 및 특이사항 (Insights)

*   **선형적 처리량 둔화 (7.5K -> 10K 구간):**
    *   7,500명 구간까지는 TPS가 꾸준히 증가했으나, 10,000명 구간에서는 향상 폭이 크게 둔화(15K -> 15.8K)되었습니다.
    *   **원인 (DB I/O 병목):** 현재 로그인 서버는 50개의 워커 스레드(Concurrent 15개)로 구동 중입니다. DB(MySQL)에 접근하며 발생하는 블로킹 시간이 누적되면서, 유휴 스레드가 모두 소진되어 OS가 더 이상 대기 중인 패킷을 처리할 스레드를 깨우지 못한 한계로 파악됩니다.
    *   **개선 방안:** 워커 스레드의 총량을 더 늘려주면 I/O 대기 중인 스레드를 우회하여 더 높은 TPS를 끌어낼 수 있습니다.
*   **균일한 레이턴시 (72ms 유지):**
    *   동시 접속이 늘어나도 레이턴시가 72ms로 고정된 이유는, 스레드가 큐에 대기하는 시간보다 **실제 DB 쿼리를 수행하고 응답받는 I/O 고정 시간(약 70ms 내외)**이 전체 지연의 대부분을 차지하기 때문입니다. 아직 서버 내부 큐에 병목이 생길 만큼 큐잉 딜레이(Queueing Delay)가 발생하지 않았음을 의미합니다.
*   **CPU 사용률 트레이드오프 (Trade-off):**
    *   목표치인 CPU 10%를 초과하여 21%를 기록했습니다. CPU 사용률을 10% 미만으로 강제하려면 IOCP의 동시 실행(Concurrent) 스레드 수를 줄이면 되지만, 이는 필연적으로 전체 처리량 하락과 레이턴시 증가를 동반합니다. 
    *   실제 초당 7,900건의 로그인을 진행하는 상황은 오픈 초기의 드문 상황을 제외하고는 일어나지 않는 상황이기 때문에 CPU 사용률이 10%를 넘는 상황은 잘 발생하지 않을 것입니다.
